## How the parts fit

```text
Member and club ── Seats web app ── seat contract ── Sputnik DAO
                         │               │
                         │               └── voter account (one per seat)
                         ├── delegate model on NEAR AI (signed receipt)
                         └── vault job on OutLayer (secure hardware)
```

## Member

Chooses the brief, reviews each delegate vote, and can override inside the window. A member can also sell the seat through a club-approved sale.

## Seat contract

Issues seats, gates resale on DAO approval, and pays the seller and the club's levy in one flow. It refuses plain transfers, so a seat only moves through an approved sale.

## Voter account

One per seat. It holds the seat's vote in the DAO, checks each delegate receipt, and enforces the override window. It is the account the DAO sees voting.

## Delegate

A NEAR-hosted model that reads each proposal, applies the brief, and writes a vote and a reason. Hard limits, such as the spend cap, are checked by code on the proposal, not left to the model.

## Keeper

A service that requests votes and casts expired ones. Anyone can cast after the deadline, so a stopped keeper can't block a vote.

## Vault job

Checks seat ownership inside secure hardware and returns vault content encrypted to the holder's key. It refuses anyone who doesn't hold a seat.

## What each part doesn't prove

The DAO record shows what the club voted. The receipt shows the signed answer the delegate gave. Neither shows what a human would have chosen, which is why the override window exists.
